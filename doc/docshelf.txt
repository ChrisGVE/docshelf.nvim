1. INTRODUCTION					    *docshelf-introduction*

docshelf.nvim downloads documentation — from https://devdocs.io and from the
other sources in |docshelf-sources| — and converts it, once, into plain text
you read in a normal buffer. Nothing is fetched again while you read: a
docset is a folder of files on disk, so opening a page and searching across
every page you have installed are both local operations.

The conversion also splits a page into its individual entries, so `List.add()`
is a page of its own rather than a heading somewhere inside the `List` page,
and the pickers list it as such.

==============================================================================
2. REQUIREMENTS					    *docshelf-requirements*

Required:
	- elinks	https://github.com/rkd77/elinks, to render HTML
	- ripgrep	for |:DocshelfSearch|
	- curl		to fetch the docsets
	- tree-sitter parsers for `html` and `markdown_inline`

For Dash docsets and hexdocs.pm (|docshelf-source-list|):
	- tar
For Dash docsets only:
	- sqlite3
For docs.rs, Maven Central and cljdoc.org:
	- unzip

One picker, either one:
	- telescope.nvim
	  https://github.com/nvim-telescope/telescope.nvim
	- snacks.nvim
	  https://github.com/folke/snacks.nvim

Without either, the plugin falls back to |vim.ui.select()|, which has no
preview and no search.

Linux and macOS. Windows is not supported; WSL may work.

3. SETUP						   *docshelf-setup*

Call `setup()` once when the plugin loads. It registers the commands; it does
not fetch anything.
>lua
	require("docshelf").setup()
<
                                                       *docshelf-from-apidocs*
Coming from apidocs.nvim: docshelf keeps its documentation in a folder of its
own, `docshelf-data` under |stdpath()| "data". To keep what apidocs.nvim
installed, move its folder before the first install: >sh
	mv ~/.local/share/nvim/apidocs-data ~/.local/share/nvim/docshelf-data
<
Everything else is renamed the same way: `:ApidocsOpen` is |:DocshelfOpen|,
`require("apidocs")` is `require("docshelf")`, and so on.

                                                            *docshelf-options*
`setup()` accepts a table:

	`picker`		string		(default: auto-detected)
		Which picker to use: `"telescope"`, `"snacks"` or
		`"ui_select"`.
		Left unset, whichever of telescope.nvim and snacks.nvim is
		installed is used.

	`layout`		string|table	(default: `"telescope"`)
		snacks.nvim only: the layout the pickers open with. Any snacks
		preset name, or a layout table. `"ivy_split"` puts the picker
		along the bottom.

	`update`		table
		Keeping installed documentation current — see
		|docshelf-updating|.

			`auto`		boolean	(default: `true`)
				Check once after Neovim settles, and
				refresh in the background.
			`every_hours`	number	(default: `24`)
				How long a check waits before the next one.

	`languages`		table
	`formats`		table
	`tools`			table
		The names a source can be linked to — see
		|docshelf-languages|. Each takes `add` to extend the built-in
		list, or `only` to replace it. An entry is a name, or a table
		naming aliases that match it too: >lua
		require("docshelf").setup({
		  languages = { add = { "Fortran", "Prolog" } },
		  tools = { add = { { "Kubernetes", aliases = { "k8s" } } } },
		})
<
	`workers`		number		(default: `4`)
		How many async jobs run at once — pages converted during an
		install, registries asked during a search. Installs
		themselves still run one at a time.

	`sources`		table		(default: all on)
		Switch a source off by its origin (|docshelf-sources|): >lua
		require("docshelf").setup({
		  sources = { ["devdocs.io"] = false },
		})
<
	`assign_key`		string|false	(default: `"<C-e>"`)
		Inside the |:DocshelfFilter| picker, the key that sets the
		language of the source under the cursor. `false` unbinds it.

	`follow_link_keymap`	string		(default: `"<C-]>"`)
		The key that follows a `local://` link from a documentation
		buffer. See |docshelf-links|.

Example, with lazy.nvim: >lua
	{
	  "ChrisGVE/docshelf.nvim",
	  dependencies = {
	    "nvim-treesitter/nvim-treesitter",
	    "folke/snacks.nvim", -- or nvim-telescope/telescope.nvim
	  },
	  cmd = { "DocshelfInstall", "DocshelfOpen", "DocshelfSearch",
	          "DocshelfFilter", "DocshelfAssignLanguage",
	          "DocshelfUpdate", "DocshelfUninstall" },
	  -- A capital letter is the same thing over every source, ignoring
	  -- the filter without clearing it.
	  keys = {
	    { "<leader>sad", "<cmd>DocshelfOpen<cr>", desc = "Docs" },
	    { "<leader>saD", "<cmd>DocshelfOpen!<cr>", desc = "Docs (all)" },
	    { "<leader>sas", "<cmd>DocshelfSearch<cr>", desc = "Grep docs" },
	    { "<leader>saS", "<cmd>DocshelfSearch!<cr>", desc = "Grep all" },
	    { "<leader>saf", "<cmd>DocshelfFilter<cr>", desc = "Filter" },
	    { "<leader>saF", "<cmd>DocshelfFilter!<cr>", desc = "Unfilter" },
	    { "<leader>sai", "<cmd>DocshelfInstall<cr>", desc = "Install" },
	    { "<leader>saI", "<cmd>DocshelfInstall!<cr>", desc = "All" },
	  },
	  config = function()
	    require("docshelf").setup({ picker = "snacks" })
	  end,
	}
<

4. COMMANDS						*docshelf-commands*

                                                            *:DocshelfInstall*
:DocshelfInstall[!]	Fetch the list of documentation sources devdocs.io
			offers and ask which ones to install.

			The picker follows the filter too, by language: with
			a filter set, only sources of the languages in it are
			offered. `!` offers every language this once, without
			clearing the filter. See |docshelf-filter|.

			With snacks.nvim, `<Tab>` marks a source and a mark
			survives a change of search, so several can be picked
			in one round.

			A row also names, at its right edge, where the source
			comes from — `devdocs.io` — so that a catalogue drawn
			from more than one place stays readable. Where the
			rows come from, and how to narrow them, is
			|docshelf-sources|.

			Installing is slow — a large source is thousands of
			pages, post-processed with tree-sitter — but it runs
			in the background and Neovim stays usable. Sources
			install one at a time from a single queue: picking
			more while one runs appends to it, a source already
			queued is reported rather than queued twice, and a
			source that fails is reported and skipped so the rest
			carry on. One notification, replaced in place, names
			the stage and the place in the queue, as in
			`2/4 lua~5.4: converting pages 310/390`.

			It happens once per source, never again while you
			read.

			Every row carries the release devdocs offers today.
			An installed source also says how what you have
			compares with it:

			`[installed]`
				the release and the build you have are the
				ones devdocs offers today.
			`[installed · rebuilt 2026-09-14]`
				the same release, but devdocs regenerated
				the source on that date.
			`[installed 3.14.6 · new release 3.14.7]`
				devdocs has moved on a patch release.
			`[installed · may be outdated]`
				installed before the plugin recorded
				anything, so nothing can be compared.

                                                     *docshelf-install-record*
			What you installed is recorded in `.installed.json`
			in the data folder (see |docshelf.data_folder()|): the
			release, the time devdocs built it, the time you
			installed it, and where it came from. It is a
			dotfile, so the |:DocshelfSearch| grep passes over it.
			Uninstalling a source drops its record.

			A source installed before origins were recorded
			counts as `devdocs.io`, since that is the only place
			it could have come from.

                                                               *:DocshelfOpen*
:DocshelfOpen[!] [{source} ...]
			Open a picker over the pages of the installed
			sources. Requires telescope.nvim or snacks.nvim for a
			preview.

			The picker follows the filter (|docshelf-filter|). `!`
			looks at every source this once, without clearing the
			filter; naming sources overrides it for this call.

                                                             *:DocshelfSearch*
:DocshelfSearch[!] [{source} ...]
			Open a picker that greps the text of the installed
			pages as you type. Requires ripgrep. Takes the filter,
			the `!` and the arguments the same way
			|:DocshelfOpen| does.

                                                             *:DocshelfFilter*
:DocshelfFilter[!] [{source} ...]
			Narrow every docshelf picker to a few sources, until
			you say otherwise. With no argument, a picker over
			the installed sources; with arguments, those sources
			directly (<Tab> completes them); with `!`, the filter
			is cleared. See |docshelf-filter|.

                                                     *:DocshelfAssignLanguage*
:DocshelfAssignLanguage {source}
			Set which language {source} documents, chosen from a
			picker. Useful for one that came out Unknown. See
			|docshelf-language-assignment|.

                                                             *:DocshelfUpdate*
:DocshelfUpdate [{source} ...]
			Install again whatever has gone out of date, from
			devdocs or from any other origin. Name sources to
			limit the round to them — <Tab> completes the
			installed ones — or give no argument to consider
			everything installed. See |docshelf-updating|.

                                                          *:DocshelfUninstall*
:DocshelfUninstall {source}
			Remove an installed source. <Tab> completes the
			installed ones. It also leaves the filter.

Both pickers can be narrowed to a few sources, and given a layout, when called
as Lua functions instead — see |docshelf-api|.

5. DOCUMENTATION SOURCES				  *docshelf-sources*

Documentation comes from a source, and a source is named by its origin — the
short address it is fetched from. devdocs.io is the one every install starts
with; the rest are listed at the end of this section.

Each source is an adapter that knows how to fetch and lay out its own pages.
Everything after the fetch — the conversion, the links, the pickers, the
filter, the update check — is the same whatever the origin, so a new source
adds a way in and changes nothing else.

                                                      *docshelf-source-folder*
A docset from a source other than devdocs lives in a folder named
`<docset>~~<origin>`, which is why two sources can each document a `text` and
neither hides the other. What you read is the docset name; the origin shows
dimmed at the right edge of a picker, and is kept in `.installed.json` (see
|docshelf-install-record|).

                                                   *docshelf-source-switching*
Every source is on by default. Switching one off by its origin removes it
from the install picker only: documentation already installed from it stays
readable and keeps updating. >lua
	require("docshelf").setup({ sources = { ["devdocs.io"] = false } })
<
                                                    *docshelf-source-registry*
devdocs ships a catalogue of everything it has, and the install picker lists
it. A package registry cannot ship one, so it is asked instead.

With snacks.nvim, from the third letter on, every enabled source that can be
searched is asked — at most `workers` of them at once — and the answers join
the list as they land, the title naming whichever registry is still being
waited on. What a registry answered is kept in `.registry_cache.json` in the
data folder, so the same name typed again is offered before any request goes
out. A row whose version the registry did not give is resolved when you pick
it. The Dash sources filter a list they fetched once rather than asking a
registry, so they are asked from the first letter.

Other pickers have no live input to drive this, and keep offering the
catalogue alone.

                                                   *docshelf-source-languages*
The install picker can be narrowed to one or more languages — the devdocs
rows and the registries alike, since a registry declares what language it
documents (hexdocs.pm declares Elixir, Erlang and Gleam, and is asked for
any of them). Dash, which spans every language, is left out: >lua
	require("docshelf").docshelf_install({
	  languages = { Haskell = true },
	})
<
                                                        *docshelf-source-list*
devdocs.io ~
	The built-in source, and the only one with a catalogue: one request
	lists every docset it has, with the release and the build time of
	each. That is also what makes the update check cheap — see
	|docshelf-updating|.

hackage.haskell.org ~
	A Haskell package. A release ships a Haddock archive
	(`/package/<name>-<version>/docs.tar`), so an install is one
	request; it becomes a page per module, plus an entry per documented
	name qualified by its module (`Data.Text.pack`). Haddock's own
	chrome — header, contents, synopsis, footer, the Source and self
	links — is dropped.

	It answers the install picker's search: three letters of a package
	name and its Hackage matches join the list. Picking one asks Hackage
	which version has documentation built, so a package whose docs never
	built is not offered.

	Installs as `<name>~<version>~~hackage.haskell.org`; its language is
	Haskell without being asked.
docs.rs ~
	A Rust crate. docs.rs builds every crates.io release and ships each
	build as one zip, so an install is a single request. It needs the
	`unzip` program.

	It answers the install picker's search: three letters of a crate
	name and its crates.io matches join the list, each already carrying
	the version that will be installed.

	Installs as `<crate>~<version>~~docs.rs`; its language is Rust
	without being asked.
Sphinx sites ~
	A Sphinx site — numpy, the Python documentation, most Read the Docs
	pages. There is no registry to search, so a site is reached by its
	address: paste the URL into the install picker and the row shows the
	project, its version, and how many pages the install will fetch.

	Read that number before you pick. Such a site ships no archive, so
	the install is one request per page — numpy is 2673 of them.

	What makes the pages readable is the site's own `objects.inv`, the
	inventory Sphinx publishes for cross-project linking: every
	documented name, the page it is on and the anchor it sits at. A link
	therefore lands on the item it names rather than at the top of its
	page.
pkg.go.dev ~
	A Go package, named by its address rather than found by a search:
	pkg.go.dev's `robots.txt` disallows its search, so there is nothing
	to type a name into. Paste a pkg.go.dev URL and the row shows the
	package, its version, and how many pages the install will fetch —
	the package the address names plus every package under it, internal
	ones excepted. The standard library is reached the same way.

	A docset's language is Go without being asked.
DocC sites ~
	Apple's frameworks, the Swift book, and anything else built with
	DocC. Named by their address: paste a documentation URL — the
	SwiftUI framework, say, or the Swift book: >
https://developer.apple.com/documentation/swiftui
https://docs.swift.org/swift-book/documentation/the-swift-programming-language
<	— and the row shows the module and how many pages the install will
	fetch.

	A DocC site publishes one JSON document per page rather than a page,
	so the install reads the site's navigator index once and then
	fetches a document per symbol. SwiftUI is over seven thousand of
	them, which is why the count is shown before you pick.

	Such a site publishes no version, so the docset carries none and
	|:DocshelfUpdate| leaves it alone rather than reinstalling it on a
	guess.
kapeli.com, contrib.kapeli.com ~
	Dash docsets: Kapeli's own feeds (about 180 — Lua, Bash, C++,
	Django, …) and the user-contributed ones (about 630 — HAProxy Lua,
	Jest, …). Two origins, because the catalogues share names — each has
	a Swift. Both are searched by name, from the first letter, since
	`C`, `Go`, `Qt` and `R` have no longer name.

	Picking a Kapeli feed asks it for its current version; a
	user-contributed row already carries it. Where Kapeli has no better
	number the version is its own (Bash installs as `Bash~9`). An install
	is one `.tgz` archive, read with `tar` and `sqlite3`. Sizes vary a
	lot — Lua is a few hundred kilobytes, C++ 173 MB — and the picker
	does not show the size before you pick.

	Dash covers every language, so a docset's language comes from its
	name: `Lua~5.5` is Lua. A name that is no language (`HAProxy_Lua`)
	is Unknown until you give it one. An archive has no website behind
	it, so a link to a page it does not hold keeps its text only.

	Installs as `<name>~<version>~~kapeli.com` or
	`~~contrib.kapeli.com`.
hexdocs.pm ~
	A package from hex.pm, the registry Elixir, Erlang and Gleam share.
	hex.pm keeps each release's documentation as one tarball, so an
	install is a single request, read with `tar`. The pages are the ones
	hexdocs.pm serves, minus sidebar, search bar, footer and icons; the
	entries are what the package's own search index lists — modules,
	functions, types, callbacks, guides, and the sections inside them
	(`Examples - Jason.decode/2`). Every shape that index has had is
	read, back to packages built in 2017. A link to another package goes
	to its page on hexdocs.pm, at the version it was built against.

	It answers the install picker's search: three letters of a package
	name and its hex.pm matches join the list, most downloaded first
	(hex.pm's search has no order of relevance), each carrying the
	version that will be installed — the newest stable release with
	documentation. A package with none is not offered.

	Installs as `<name>~<version>~~hexdocs.pm`. Its language is read
	from the docs: Gleam's index names it, and ExDoc links a stylesheet
	per language. `jason` is Elixir, `telemetry` Erlang, `gleam_stdlib`
	Gleam.
pkg.odin-lang.org ~
	The packages that ship with the Odin compiler. Odin has no package
	manager, so there is nothing to search: typing `odin` offers two
	docsets. `odin` is the `base` and `core` collections — the standard
	library, and so Odin's reference — and `odin_vendor` the `vendor`
	bindings (raylib, SDL, Vulkan, …). Picking one reads the version the
	site documents from the first line of its catalogue.

	Each package is an entry named by its import path (`encoding/json`),
	each declaration one qualified by it (`encoding/json.marshal`). An
	install fetches a page per package (180 for `odin`, 56 for
	`odin_vendor` in September 2026). A link to a package the docset does
	not hold goes to its page on the site. Both are large: `odin` is about
	70,000 entries and 350 MB, twenty minutes to install on an M-series
	Mac; `odin_vendor` about 29,000 entries, 145 MB and ten minutes.

	Installs as `odin~<version>~~pkg.odin-lang.org`. The site only
	documents the newest build, so an install holds today's version.
metacpan.org ~
	A Perl distribution from CPAN, read through MetaCPAN's API. It
	answers the install picker's search: three letters and the
	distributions whose modules MetaCPAN suggests join the list, each
	once, carrying the version of its latest release. `perl` itself is
	one of them and, named for the language, becomes Perl's reference.

	An install fetches the POD of every documented file of the release.
	Each module is an entry (`Moose::Util`), and so is every heading below
	the top level and every `=item`, named after the module (`Moose::Util
	is_role($package_or_obj)`) and typed by the section holding it
	(`Methods`). A link to a module the docset holds names its page; any
	other goes to metacpan.org. `Moose` is about 1,500 entries and half a
	minute to install; `perl` about 12,400 entries, 62 MB and five
	minutes on an M-series Mac.

	Installs as `<distribution>~<version>~~metacpan.org`, the version the
	release is named for (`perl-5.44.0` gives `perl~5.44.0`).
Maven Central ~
	A Java, Kotlin or Scala library from Maven Central, origin
	`central.sonatype.com`. An install is the release's `-javadoc.jar`,
	the HTML its build generated, read with `unzip`. It answers the
	install picker's search: three letters and the artifacts that ship
	such a jar join the list, each carrying its newest release.

	The entries are what the jar's own search index lists, whichever
	generator wrote it: javadoc (since JDK 11, or the older
	`index-all.html`), Scala 3 or Scala 2 scaladoc, or Kotlin's Dokka.
	The language is the generator's: javadoc Java, scaladoc Scala, Dokka
	Kotlin. Class-use pages, trees and lists are left out, and a link to
	one goes to javadoc.io. A library that publishes an empty placeholder
	jar (okhttp, kotlinx-coroutines) is refused. `commons-lang3` is about
	4,600 entries, 29 MB and a minute and a half on an M-series Mac.

	Installs as `<artifact>@<group>~<version>~~central.sonatype.com`: an
	artifact's name alone is ambiguous (two unrelated `cats-core` exist).
gemdocs.org ~
	A Ruby gem, its YARD documentation as gemdocs.org builds it. It
	answers the install picker's search: three letters and the gems
	rubygems.org finds join the list, the most downloaded first, without
	a version: gemdocs does not always have the newest release built, so
	a pick installs the newest version gemdocs has.

	The entries are YARD's own lists: every class and module, every
	method as Ruby writes it (`Nokogiri::XML::NodeSet#css`,
	`Nokogiri::HTML4::Document.parse`, operators such as `NodeSet#&`
	included), every constant, and the extra files such as the README.
	The source code under each method is left out. A link to a page the
	docset holds names it; any other goes to gemdocs.org.

	Installs as `<gem>~<version>~~gemdocs.org`.
crystal-lang.org ~
	Crystal's standard library. Crystal has no central package registry,
	so there is one docset, `crystal`, offered at the newest release and,
	named for the language, Crystal's reference.

	An install reads the site's index of the whole API, then fetches a
	page per type. Every type is an entry (`Atomic::Flag`), and so is
	every constructor, class method and macro (`Array.new(initial_capacity
	: Int)`), instance method (`Array#&(other : Array(U))`) and constant
	(`Signal::INT`); each overload is its own entry. The top level's
	methods and macros (`puts`, `record`) have no type. A link to a page
	the docset holds names it; any other goes to crystal-lang.org.
	Crystal 1.21.0 is about 17,300 entries, 89 MB and nine minutes on an
	M-series Mac.

	Installs as `crystal~<version>~~crystal-lang.org`.
ocaml.org ~
	OCaml packages: ocaml.org builds every opam package's documentation
	with odoc. Three letters and the packages it finds join the list,
	best match first, each with its newest version; a package without
	documentation is left out. OCaml's standard library is on devdocs.

	An install reads odoc's own search index, then fetches a page per
	module, module type, class and extra file. Every module, type,
	value, exception, constructor, field, method and extension is an
	entry, named as odoc names it (`Lwt.bind`, `Lwt.state.Return`,
	`Lwt.Infix.(>>=)`); so is each library's module list and each extra
	file such as the README. Links to source listings are left out. A
	link to a page the docset holds names it; any other, another
	package's included, goes to ocaml.org.
	lwt 6.1.2 is about 1,300 entries, 5.7 MB and 42 seconds on an
	M-series Mac.

	Installs as `<package>~<version>~~ocaml.org`.
Documenter sites ~
	Julia packages, from the site each one publishes with Documenter.jl.
	Typing part of a name searches the General registry; a pick reads
	the package's GitHub Pages site (`<owner>.github.io/<Package>.jl/
	stable/`, redirected to its own domain where it has one). A package
	documented elsewhere (Plots, Makie) is installed by pasting the
	address of any page of its documentation, as for a Sphinx site.
	Julia's own manual is on devdocs.

	An install reads the site's search index, then fetches a page per
	page. Every page, section and docstring is an entry, typed as
	function, method, type, macro, constant, keyword or module; each
	method of a function is its own entry. A link to a page the docset
	holds names it; any other goes back to the site. DataFrames 1.8.2 is
	2.7 MB and 19 seconds on an M-series Mac.

	Installs as `<Package>~<version>~~documenter`. The site is remembered
	in `.documenter_sites.json`, so an update asks it again.
cljdoc.org ~
	Clojure and ClojureScript libraries from Clojars and Maven Central.
	Three letters and the libraries cljdoc finds join the list, named
	`artifact@group` (`ring-core@ring`), without a version: a pick
	installs the version cljdoc shows by default. A version cljdoc has
	not built cannot be installed; asking for it at cljdoc.org starts a
	build.

	An install reads cljdoc's search set and its offline bundle, one zip
	(read with `unzip`). Every namespace, var, macro, protocol, protocol
	method and multimethod is an entry, named as Clojure writes it
	(`ring.util.response/redirect`, `clojure.core.async/>!`); so is every
	article and each of its sections. The raw docstrings are left out. A
	link to a page the docset holds names it; any other goes to
	cljdoc.org. malli 0.20.2 is about 1,000 entries, 5 MB and 40 seconds
	on an M-series Mac.

	Installs as `<artifact>@<group>~<version>~~cljdoc.org`.

6. KEEPING DOCS CURRENT					*docshelf-updating*

Documentation moves on, and it does so differently depending on where it came
from.

A devdocs source gets a new patch release (3.14.6 becomes 3.14.7), or keeps
its release and is rebuilt from newer upstream pages. Both are recorded at
install time (see |docshelf-install-record|), so both can be noticed, and the
source is refreshed in its existing folder.

A source from anywhere else is asked what version its origin offers today.
Since such a docset is usually named for the version it holds, updating it is
an install under a new name: `text~2.1.2` becomes `text~2.1.3` and the old
folder is removed once the new one is in place. The language you assigned it
(see |docshelf-language-assignment|) and its place in the filter are carried
across, so an update does not undo what you had arranged.

|:DocshelfUpdate| installs again every source found in one of those states.
Three are left alone on purpose:

	- one installed before the plugin recorded anything, because there is
	  nothing to compare it against;
	- one devdocs no longer lists, because reinstalling it would be a
	  guess about what replaced it;
	- one whose origin publishes no version at all, for the same reason —
	  there is nothing to compare.

An update is an ordinary install, so it uses the same queue and the same
progress notification, and Neovim stays usable throughout.

                                                        *docshelf-update-auto*
The same check also runs on its own: the first time you pause after opening
Neovim, and then at most once every `every_hours`. It is armed by `setup()`,
so a plugin loaded lazily on its commands first checks once you have opened
the docs, not at startup. The time of the last check is kept in `.update.json`
in the data folder.

To leave updating to |:DocshelfUpdate| alone, or to check less often: >lua
	require("docshelf").setup({ update = { auto = false } })
	require("docshelf").setup({ update = { every_hours = 72 } })
<
==============================================================================
7. LANGUAGES					       *docshelf-languages*

Every installed source is linked to a language, so that a set of sources can
be talked about by what it is about rather than by slug. `python~3.14`,
`numpy~2.5` and `scikit_learn` are all Python; `git` is Git and `docker` is
Docker, because "language" here is one flat field covering a programming
language, a file format or a tool alike.

                                                 *docshelf-language-reference*
Within a language, one source is its reference: the one whose name before `~`
is the language's own name or one of its aliases — `python~3.15` for Python,
`openjdk~21` for Java. The others belong to the language. That distinction is
what lets a selection widen itself: choosing Python's reference brings in the
Python libraries with it, while choosing `numpy~2.5` on its own brings in
nothing, and a different version of the reference (`python~3.13`) is not
pulled in either.

                                                       *docshelf-language-set*
The names come from three lists — `languages`, `formats` and `tools` — which
are joined into one. They ship with sensible contents (Python, Rust, Go,
Haskell, Odin, Zig … Markdown, JSON, YAML, TOML, Typst … Git, Docker, tmux,
Neovim, jq, ripgrep …), each SQL engine is a name of its own rather than a
flavour of SQL, and LaTeX, TeX and BibTeX are kept apart. Extend or replace
them through `setup()`; see |docshelf-options|.

                                                *docshelf-language-assignment*
A source's language is decided once, when it is installed, and kept in
`.installed.json` (see |docshelf-install-record|). In order:

	1. a source that declares its own language is believed — a Hackage
	   package is Haskell;
	2. a devdocs source listed in `lua/docshelf/source_languages.lua`, a
	   table kept by hand, takes that table's answer;
	3. otherwise, a source whose name before `~` is a name or an alias
	   from your lists gets that name;
	4. anything left is Unknown.

|docshelf.assign_language()| gives any installed source a name, replacing
whatever it had, and the choice survives a refresh, an update and a
reinstall. Its picker lists your names plus every language already recorded
on an installed source, narrowing as you type; when what you type names none
of them, the first row offers it as a new name, so a language you need once
costs no configuration.

                                                     *docshelf-language-drift*
Because `source_languages.lua` is kept by hand, it drifts as devdocs adds and
retires sources. To compare it with the live catalogue: >
	nvim --headless -l scripts/check_source_languages.lua
<
It lists the sources the table lacks — each with a proposed row seeded from
that project's GitHub language, for a person to check — and the rows for
sources devdocs no longer lists. It never edits the table, and it cannot tell
that a row already there is wrong.

8. NARROWING TO A FEW SOURCES				  *docshelf-filter*

With a handful of sources installed, a picker can list all of them. With
several dozen, a list of everything is no longer a list of what you need.
|:DocshelfFilter| picks a few and keeps them, and |:DocshelfOpen| and
|:DocshelfSearch| then look only inside them, and |:DocshelfInstall| offers
only the languages they are written in — so a filtered session narrows what
you read, what you search and what you are offered to add.

The filter belongs to this Neovim session, so a Rust session and a Python
session each keep their own, and neither has to be undone afterwards.

Narrowing is not only about reading a shorter list. A grep is one ripgrep run
over the sources in play, so the filter is also what keeps |:DocshelfSearch|
fast as the collection grows.

                                                      *docshelf-filter-picker*
Run |:DocshelfFilter| with no argument for a picker over the installed
sources; with snacks.nvim, `<Tab>` ticks several. Rows read
`language | source`, so typing a language narrows to it — `Unknown`
included. A filled dot marks a source you picked, a hollow one a source a
language brought along (see |docshelf-language-reference|): picking
`python~3.14` brings `numpy~2.5` and `scikit_learn` with it, while
`numpy~2.5` picked on its own stays on its own.

`<C-e>` on a row sets that source's language and redraws the list, which is
the quick way to deal with an `Unknown`. The key is the `assign_key` option;
see |docshelf-options|.

                                                    *docshelf-filter-ignoring*
Three ways past the filter, none of which clears it:

	- `!` — |:DocshelfOpen|, |:DocshelfSearch| and |:DocshelfInstall|
	  with a bang look at everything this once. A capital letter in a
	  keymap is a good home for it.
	- naming sources — `:DocshelfOpen rust` overrides the filter for that
	  call.
	- `follow_filter = false` in the Lua options, which is what `!`
	  passes.

|:DocshelfFilter| with a bang clears it, and uninstalling a source drops it
from it.

==============================================================================
9. READING A PAGE					 *docshelf-reading*

A documentation page is an ordinary buffer holding text, so every Neovim
motion, search and mark works on it. The plugin sets 'conceallevel' and
'concealcursor' on the window it opens so that link markup and inline code
fences read as text rather than as punctuation.

==============================================================================
10. FOLLOWING LINKS					   *docshelf-links*

Links are numbered in the text — `[1]`, `[2]` — and the addresses themselves
are collected in a footer at the end of the page. Following one is therefore
two steps, and it only works in an opened document: a picker preview is not
enough.

	1. Put the cursor on the link number and press `*`. That searches for
	   the same number in the footer and lands on the address.
	2. From there:
	   - a `local://` address is another installed page: press the
	     `follow_link_keymap` key, |CTRL-]| by default.
	   - anything else is a URL: open it as you normally would, for
	     instance with |gx|.

A link to a page the docset does not hold becomes that page's address on
the web: devdocs.io for a devdocs source, the documentation's own site for
every other source.

When a link points at one spot inside a long page, the jump is done by
searching for the text it names, so you may need |n| to reach it — the first
match is not always the one meant.

11. LUA API						     *docshelf-api*

                                                    *docshelf.docshelf_open()*
`require("docshelf").docshelf_open(`{opts}`)`
		|:DocshelfOpen| as a function. {opts} may carry:
			`restrict_sources`	list of source names to list
			`layout`		snacks layout, as in `setup()`
>lua
		require("docshelf").docshelf_open({
		  restrict_sources = { "rust" },
		  layout = "ivy_split",
		})
<
                                                  *docshelf.docshelf_search()*
`require("docshelf").docshelf_search(`{opts}`)`
		|:DocshelfSearch| as a function. Takes the same {opts}.

                                                   *docshelf.ensure_install()*
`require("docshelf").ensure_install(`{sources}`)`
		Install every source in the list that is not installed yet,
		and do nothing for the ones that are. The missing ones join
		the same queue |:DocshelfInstall| uses, so they never install
		alongside each other or alongside a source picked there.
		Meant to be called after `setup()` so a configuration carries
		its own docsets: >lua
		require("docshelf").ensure_install({ "lua~5.4", "rust" })
<
                                                  *docshelf.docshelf_filter()*
`require("docshelf").docshelf_filter()`
		|:DocshelfFilter| as a function — open the filter picker.

*docshelf.filter*
`require("docshelf").filter`
		The filter itself:
			`set(`{names}`)`	narrow to these sources
			`clear()`	drop the filter
			`active()`	the sources picked, or nil
			`languages()`	what those are written in
			`installed()`	every installed source

		Every picker call takes `follow_filter = false` to ignore the
		filter once, which is what the `!` commands pass.

*docshelf.assign_language()*
`require("docshelf").assign_language(`{slug}`)`
		Open a picker and link {slug} to the language chosen there.
		See |docshelf-language-assignment|.

*docshelf.languages.pulled_in()*
`require("docshelf.languages").pulled_in(`{selected}`, `{installed}`)`
		For every language reference in {selected}, the other
		installed sources of that language — what a selection widens
		to. See |docshelf-language-reference|.

*docshelf.languages.unknown()*
`require("docshelf.languages").unknown(`{installed}`)`
		The installed sources whose language could not be decided.

*docshelf.metadata.installed_origins()*
`require("docshelf.metadata").installed_origins(`{slugs}`)`
		Where each of {slugs} came from, as a table keyed by slug.
		For a picker of its own over the installed sources, so it can
		show the same origin the install picker does.

                                                      *docshelf.data_folder()*
`require("docshelf").data_folder()`
		The folder the converted pages live in.

                                           *docshelf.open_doc_in_new_window()*
`require("docshelf").open_doc_in_new_window(`{path}`)`
		Open one page in a new window, with conceal and link
		following set up. 'winfixbuf' is set.

                                           *docshelf.open_doc_in_cur_window()*
`require("docshelf").open_doc_in_cur_window(`{path}`)`
		The same, in the current window, without 'winfixbuf'.

                                               *docshelf.load_doc_in_buffer()*
`require("docshelf").load_doc_in_buffer(`{buf}`, `{path}`)`
		Load one page into an existing buffer. Nothing is set up for
		you: set 'conceallevel' to 2 and 'concealcursor' to `"n"`
		on the window yourself, and link following is not wired.
		This is the entry point for a picker preview, not for
		standalone display.
